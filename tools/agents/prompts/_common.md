## 一、规则（必须遵守）

1. **事实优先级**（冲突时从高到低；文件不存在就跳过该层）：
   1. `docs/decisions/author-decisions.md` 中作者已填写的决定；

   4. 各文档按基准 §18 的唯一归属：概念只在归属文档中定义，其他文档只引用（写"见 `design/05` §4.2"），不重定义。
2. **只修改"你负责的文件"**（第二节）。其他文件一律不改，包括基准、`TODO.md` 和其他文档。发现其他文档需要改，写进报告第 6 节。调度器会丢弃你对其他文件的改动。
3. **不要执行改变仓库状态的 git 命令**（commit、push、checkout、switch、reset、stash、rebase、merge 等），提交由调度器完成。可以用 `git log`、`git show`、`git diff`、`git grep` 查看。
4. **格式沿用现有文档**：
   - 策划文档文首用引用块写"归属（基准 §18）/ 上游 / 引用而不重定义 / 标注约定"，参考 `docs/design/05-martial-arts-system.md` 前 9 行；技术文档文首用"项 / 内容"表格，参考 `docs/tech/03-mobile-performance.md` 前 11 行，其后写"结论先行（TL;DR）"。
   - 标注：**（原创扩展）** 原著没有的内容；**（待考）** 原著事实尚需逐字核对；**（待核实）** 技术事实（版本、价格、API、限额）尚未联网确认；**（待实测）** 需要真机或真账号验证；**【建议值】** 依赖其他文档，先给可用数值并在文末登记。
   - 策划文档文末依次为：`本文新增术语与 ID`、`数据校验规则与测试用例`（适用时）、`待决事项 / 依赖`（小节：替下游给出的建议值 / 本文依赖的上游事实 / 对基准的修改提案 / 原著考据待办 / 开放问题（附默认值））。技术文档文末依次为：`参考资料`、`本文新增术语/约定`、`待决事项 / 依赖`。
5. **ID** 按基准 §12 命名。新建 ID 前先全仓库搜索（如 `grep -rn "sk_taizu" docs`），能复用就复用，避免重名；旧 ID 按 `rulings-v1.md` 的重命名表替换。
6. **数值**要能从基准 §3–§5、§9 与 `design/03`、`04`、`05` 的公式推出。关键数值写出算式或核算过程，不要凭空给数字。
7. **原著考据**以三联/广州修订版为基线（基准 §16 第 6 条）。只写有把握的原著事实；没把握就标（待考），写明要核对什么（书名、回目、人物或情节）。**不要编造引文、回目号、人名或招名。** 原著没有的内容标（原创扩展）。
8. **分节写入，防止截断**：长文档每写完一节就保存到文件，不要一次输出上千行。结束前通读全文，确认：没有截断的句子和表格；代码块成对闭合；目录与正文一致；没有"TODO""此处省略""待补充"之类的占位。
9. **不要停下来提问**，也不会有人回答。需要作者拍板的事项先给默认值、继续完成，并列入文档的"开放问题"和报告第 4 节。
10. 已有的"待决事项"条目不要删除；已解决的改写为"已解决：……（见 X §Y）"，便于追溯。
11. 报告必须如实：没做完、没核实、没把握的都要写出来。
