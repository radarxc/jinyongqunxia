## 0. 结论先行（TL;DR）与关键决策

**一句话**：以“**工笔为骨、水墨为气**”定风格；人物与三视图走 `codex exec`，Gemini 只出物品；角色按“**审定设定卡 → `image_gen` 一张三视图 → 工具切件 / 关键点旁注 → 代码或 CC0 动作轨迹 → 装备层确定性派生**”生产，所有候选经登记、人工审核与母版哈希入库。

执行时必须同时满足五个闸门：`packages/spec/` 是跨语言静态契约唯一目录；书眠成片固定为 13 条 `vid_sleep_NN_MM`、目标 24 秒；标准男女切件产物为 `2×3×13=78` 张，另按 AR-29 为具名 NPC 生产身份 rig，行走/待机不制作帧表；地图、189 城、99 门派与 NPC/变体需求只从归属文档和 `tech/04` 引用图派生；角色 rig 图集不得突破 `tech/03` 的 40/105/170/300 MB 硬上限。完整包量与真机峰值仍须 Phase 0 实测。

### 2.1 总体风格："工笔为骨、水墨为气"

| 档位 | ID | 用途 | 线条 | 设色 | 背景/留白 | 参照气质（仅描述，不作图生图源） |

| S2 水墨写意 | `shuimo_scene` | 场景概念、大地图、过场背景、书眠/天书视频 | 皴擦点染，山石用斧劈/披麻皴意象，远景只用墨色层次 | 以墨为主，局部点青绿/赭石；"墨分五色" | 留白 ≥ 35%，云雾、水面、天空大块留白 | 宋元山水"三远法"（高远/深远/平远） |
| S3 游戏化工笔 | `gongbi_game` | 精灵、图标、UI、特效贴图 | 外轮廓线加粗（成品 2–3 px），内部线简化 | 2–3 阶色阶（亮/中/暗）+ 一道描边；饱和度比 S1 高 10–15%，保证手机小屏可读 | 图标主体居中占 70–80%，背景纸纹或透明 | 工笔的线 + 版画的清晰剪影 |

**统一原则**
1. **线是灵魂**：任何档位都必须有可辨识的墨线；禁止无线条的"厚涂写实"与"3D 渲染塑料感"。
2. **墨先于色**：先保证灰度下层次成立（审核时一律加一张灰度预览），再看颜色。
3. **纸在画下**：纸纹/绢纹由**运行时屏幕空间叠加**（tech/02 后处理）统一提供；母版中只允许 S1/S2 带轻微纸纹，**S3 精灵与图标一律不烘焙纸纹**（否则缩放、镜像、图集拼接会穿帮）。
4. **少即是多**：同屏主色 ≤ 3 种 + 墨色；品阶金只在天阶出现，避免"满屏金光"。

### 2.5 构图与留白（S1 CG / S2 场景）

1. **三远法取景**：大场景（华山、光明顶、侠客岛）用高远（仰视、竖构图裁切）；江湖路途用平远（横向、地平线低）；庭院/古墓用深远（层层门洞纵深）。
2. **留白比例**：CG ≥ 25%，场景概念 ≥ 35%；留白处用于放置 UI 文本与题跋。
3. **题跋与印章**：CG 可留出右上/左上竖排题跋区；**文字一律后期用字体排版**（§2.9 禁止项 7），印章用程序化生成的朱文/白文印（字体 + 印泥纹理）。
4. **人物与环境比例**：戏剧性 CG 人物占画高 40–60%；意境 CG（天书现世、书眠）人物可小至 10%，突出天地。
5. **视线引导**：以墨色最重处 + 朱砂点缀为视觉焦点，每张 CG 只有一个焦点。

### 4.1 选型原则

1. **当前入口白名单**：人物与三视图由 `codex exec` 自动落盘；TraeX 仅处理既有非人物类型；Gemini 网页结果须人工下载登记且只能用于物品。任何新供应商先改作者决定/配置白名单，再接适配器。
2. **母版可落地**：每个接受的候选立即保存原文件、提示词、参考图 ID、生成时间、工具展示版本和 SHA-256；不把云端“作品库”当长期存储。
3. **能力适配器化**：管线抽象 `t2i`、`edit_multi_ref`、`img2mesh`、`i2v`、`tts`，但未启用适配器必须返回“未授权”，不能静默回退到另一服务。
4. **许可与隐私先于质量**：上传金庸人物设定卡前核对输入/输出权利、训练使用、公开画廊和删除机制；许可不清即不用。OFL 标题字体也逐字体保存 `OFL.txt` 与版本哈希（P04）。
5. **不把公开说明当账号实测**：实际可访问性、配额、水印、导出分辨率与地区限制在账号上记录**（待实测）**；本节只缩小未知范围。

## 5. 分类型生成管线

> 每条管线统一按"**输入 → 步骤 → 工具 → 质检 → 输出规格 → 入库**"书写。确定性处理由 `tsgen` CLI 驱动；`codex exec`、TraeX 与 Gemini 手工导入均须登记。`provenance` 必须写入口、提示词、参考图、生成时间、界面显示模型（若有）和文件哈希；供应商不暴露种子时写 `seed: null`，不得伪造可复现性。

**通用生命周期**（所有类型共用，状态机详见 §6.5）：

```mermaid
flowchart LR
  A[登记需求<br/>status=todo] --> B[渲染提示词<br/>模板+角色卡+风格]
  B --> C[批量生成候选<br/>N 张/条]
  C --> D[自动初筛<br/>尺寸/透明/人脸数/相似度]
  D --> E[人工挑选+修图<br/>status=review]
  E -->|通过| F[写母版+元数据<br/>status=approved]
  E -->|打回| B
  F --> G[tech/06 构建<br/>runtime 产物+manifest]
```

### 5.1 原画/概念图与剧情 CG（`art_`、`cg_`）

| 环节 | 内容 |
|---|---|
| 输入 | `design/chapters` 的区域/主线条目（`rg_*`、`q_*`）；CG 分镜卡（YAML：镜头、在场角色 ID 与变体、情绪、构图法、留白位置）；角色设定卡 `ref_*` |
| 步骤 | ① 通过 `codex exec` 生成 8–16 张构图候选，全部只作候选而非自动入库 → ② 选定构图后，必要时在 Blender 用白模/人偶摆位并导出深度或线稿（多人 CG 原则上执行）→ ③ 以设定卡、构图草图和风格金样本作参考生成底图 → ④ 按人物区域逐人编辑，每次只改变一个角色或一个明确问题 → ⑤ Krita 手修手、兵器、右衽和服饰纹样 → ⑥ 直接生成到足够母版尺寸，或只做确定性缩放；不得把未启用超分模型写成必经步骤 → ⑦ 套用书界 LUT、校正留白并审定 |
| 工具 | `codex exec` / `image_gen`；Blender（摆位）；Krita（手修）；FFmpeg/色彩脚本（确定性处理） |
| 质检 | 通用清单 + CG 专项：人物识别锚一致（与设定卡并排比对）；人数与分镜一致；视线/动作逻辑；时代服饰；无画内文字；**未水平翻转**；留白区满足 UI 文本需求 |
| 输出规格 | 母版 3840×2160 PNG（sRGB）；如经人工拆层则另存 `layers/` 供视频视差复用；概念图 2560×1440 即可 |
| 入库 | `content/assets/registry/ch01/cg.yaml` 条目；母版写入外置 `/art/master/cg/ch01/`；`provenance` 记录入口、界面显示模型（若有）、提示词、参考图 ID、时间与 SHA-256；网页端无种子时明确记 `seed: null` |

**CG 数量控制**：同一幕优先"一张 CG + 立绘演出"，只有锚点事件、改命、羁绊高潮才配 CG。

### 5.2 立绘（`por_`）

```mermaid
flowchart TD
  C0[角色卡 YAML<br/>识别锚·时代·体型·配色] --> C1[设定卡生成<br/>正/侧/背/3/4 + 面部特写]
  C1 --> C2{人工审定<br/>golden reference}
  C2 -->|S 级| C3[派生参考集 12-24 张<br/>逐张审定]
  C2 -->|A/B/C 级| C5[多参考生成<br/>一次只改一个变量]
  C3 --> C5
  C5 --> C6[修图: 手/兵器/服饰纹样]
  C6 --> C7[表情差分<br/>脸部局部重绘 × 6-8]
  C7 --> C8[可选人工分层<br/>轻量 CSS/网格动画]
  C8 --> C9[抠图/规格化<br/>透明输出或人工蒙版]
  C9 --> C10[母版 + 补丁 + 元数据]
```

| 环节 | 内容 |
|---|---|
| 输入 | 角色卡 `tools/aigc/prompts/characters/<npc_id>.yaml`（§7.1）；`design/chapters` 的人物描述；时代服饰表（§2.7） |
| 步骤 1 设定卡 | 生成 **turnaround 设定卡**：同一画布上正面/侧面/背面/3/4 全身 + 面部特写 + 兵器特写，纯白底，S1 风格但线条更清晰。通过 `codex exec` 出 8–16 张候选，人工挑 1 张，再逐项修到满足角色卡识别锚。审定后登记为 `ref_<id>__<variant>_sheet`，**此后不原位覆盖**；修改须升版本并令下游变为 `stale` |
| 步骤 2 一致性控制 | S 级：以设定卡为源派生 12–24 张姿势/光照/景别参考，逐张勾选锚点后形成参考集；A/B/C 级按重要度缩减参考数。当前统一采用多参考编辑，不训练角色 LoRA（P02）；参考集可在未来获授权后复用为训练候选，但不能自动视作合格训练集 |
| 步骤 3 基础立绘 | 统一姿势模板：站姿 3/4 侧、重心稳定、兵器位置按角色卡；构图 2:3，脚底留 4% 边距；背景纯色（便于抠图） |
| 步骤 4 表情差分 | 只重绘**脸部区域**（蒙版：发际线至下颌，含耳）：平静 `e_neutral`、喜 `e_joy`、怒 `e_angry`、哀 `e_sad`、惊 `e_surprise`、战斗 `e_battle` + 角色特有。固定设定卡、裁区和提示词骨架，每次只修改情绪词；若入口暴露种子则一并固定，否则记 `seed: null`。输出为**脸部补丁**（含偏移坐标），不重复存整张 |
| 步骤 5 分层（可选） | 仅为呼吸/眨眼拆 `body`、`hair_back`、`hair_front`、`face_base`、`eyes_open`、`eyes_closed`、`mouth_*`、`accessory`；透明输出不足时在 Krita 手工修层边。运行时只采用 CSS 位移/缩放或 tech/02 网格微变形，不走 Spine/Live2D 主线（P55）。书灵按 P54 是抽象墨影 + 对话立绘框架、非战斗单位，不制作角色骨骼或战斗精灵 |
| 步骤 6 抠图与规格化 | 优先请求透明输出；否则在 Krita 手工蒙版。边缘 1 px 收缩 + 去白边（去预乘）→ 统一画布 2048×3072、人物脚底对齐基线 y=2950 → 线条色校正到 `ink.nong`。BiRefNet 仅为日后允许本地模型时的候选，不进入当前命令 |
| 工具 | `codex exec` / `image_gen`；Krita；确定性图像规格化脚本 |
| 质检 | 设定卡识别锚逐项勾选；手指数量/关节；兵器握持方向；右衽；表情差分**与基础脸同一人**（并排闪烁对比）；补丁接缝不可见；透明边无白边；64 px 剪影可辨 |
| 输出规格 | `por_<id>__<variant>_base.png` 2048×3072 RGBA；`por_<id>__<variant>_e_<emo>.png` 脸部补丁（典型 640×640）+ `…_patches.json`（偏移、尺寸）；可选 `…_layers/`（PSD 或分层 PNG + `layers.json`） |

### 5.4 角色分层部件与装备层（重点）

#### 5.4.1 路线决策（2026-10-01 AR-22；2026-10-02 AR-29）

| 维度 | **分层部件 + 代码 / 动作轨迹（采用）** | 整身预渲染帧（仅 cutin） |
|---|---|---|
| 移动动画 | 16 个运行时 part 按闭式曲线变换；无帧表 | 每角色、动作、方向重复出帧 |
| 换装 | 具体兵器、衣甲、头饰、鞋等替换/覆盖既有槽 | 每种组合都需重渲 |
| 方向 | 三视图 + 镜像解析 `Dir8` | 需完整八向 |
| 一致性 | pivot/childJoint/template 与金样约束 | 单帧完整，但批量组合成本高 |
| 生产基数 | 每角色 / 体型 1 张三视图设定图，工具切为 39 张源件；标准男女切件产物共 78 张，装备层按物品增量 | 随角色数×动作数×方向数增长 |
| 结论 | 行走默认程序步态；战斗大动作接动作库轨迹 | 不用于战斗动画，只用于立绘切入 |

人物与三视图均不得再送 Gemini（AR-31 / AR-34）；Gemini 只保留物品生产入口。每张 sheet 自动检查三栏同人、同装、栏序和腋下 / 双腿间背景，再人工逐项核识别锚。原型 Q1 固定核 5 条锚：发髻、短褐主色、腰带色与结位、裤色、绑腿和鞋，须 `5/5`；主色 Lab 前三色与已审立绘 `ΔE2000≤10`。Q1 阈值为调研报告 §5.6 的**【建议值】**，待样张复核。任一失败可按同一提示词重出，整张最多重试 2 次【建议值】；仍失败则转人工修图 / 单栏补图，不得无限消耗额度。

#### 5.4.5 渲染风格化

| 手段 | 做法 |
|---|---|
| 描边 | 在 256 px/m 源图烘焙 2 px 外轮廓；缩档以 alpha coverage 保持，不运行时扩边 |
| 内部线 | 领口、褶皱与甲片只画能在 64 ppm 读出的一级结构线 |
| 着色 | 2–3 阶平涂；方向光由可选法线计算，颜色图烘焙形体明暗不超过 15% |
| 纹样 | 每个槽单独检查，不得跨 pivot/裁边依赖相邻部件；64 ppm 读不出的纹样简化 |
| 抗锯齿 | 母版直接 256 ppm；离线预乘 alpha 后 Lanczos3 缩到 128/96/64，再还原 alpha |

#### 5.4.6 显存预算（供 tech/03 决策）

旧帧数模型全部失效，不用理论“省了多少”替代打包报告。构建按实际裁边面积 `A_i` 计算：颜色 mip0+1 约 `ΣA_i×bpp/8×1.25/η`，`η` 为装箱率；半分辨率法线再加颜色面积的 25%。**（初值，待 ENG-12 实测）**

| 档 | ppm / 法线 | 角色 rig 图集硬限 | 构建与运行要求 |
|---|---|---:|---|
| low | 64 / 无 | 40 MB | 基础 + 当前区域装备；超限先删不可见层 |
| mid | 96 / 有 | 105 MB | 按区域 LRU；不得降具体神兵为光色 |
| high | 128 / 有 | 170 MB | 记录基础、装备、法线各自字节 |
| ultra | 128 / 有 | 300 MB 名义；实际角色工作集 ≤256 MB | 服从 `tech/02`/`tech/03` 全局 512 MB |

运行压力上限为 100 角色×20 实例=2,000 实例，动态实例数据 `2,000×56 B=112,000 B/帧`；这不是纹理显存。Phase 0 必须用 78 张基础源件、满载装备组合与三区域切换测下载、转码峰值和 GPU 工作集。

#### 5.4.7 TOOL-rig-pipeline 的物品派生

管线实现任务名为 TOOL-rig-pipeline；本文件只说明资产生产入口，算法权威值见 `tech/09-rig` §3。

```bash
python3 tools/rig/build_item.py \
  --input /art/master/item/eq_example.png \
  --item-id eq_example --class weapon \
  --rig assets/default/rig/male_std/manifest.yaml
```

| 阶段 | 固定规则 | 产物 |
|---|---|---|
| 抠底 | 边界连通近象牙底 `RGB≈(230,225,216)`；ΔE76 阈值 18，10–22 羽化并去色溢 | 透明 RGBA 工作图 |
| 裁边 | `alpha≥8/255` 包围盒；补 `ceil(8%×max(w,h))`，至少 4 px | 稳定裁边图 |
| 图标 | 256 母图下采 128/64/32；alpha 预乘缩放 | `assets/default/item/<类>/icons/<id>_<size>.png` |
| 武器层 | PCA 主轴摆正；按子类握点比例与名录长度/默认长度换算 ppm | `<id>__weapon_R.png`，必要时含 L |
| 软装备层 | 槽位 SVG mask；k-means 取 3–5 主色，中心 1/3 纹理片平铺 | `assets/default/item/<类>/layers/<id>__<slot>.png` |
| 元数据 | 每个 slot PNG 横排三视图 cell；写 slot、view、file、sourceRect、pivot、scale、zOrder、tint | 类别目录共用 `layers/layers.yaml`，以 `items[]` 分隔 |

任一步触发失败条件都进入人工修图队列，不得用随机重试掩盖。相同输入哈希、配置与工具版本必须逐像素复现。

管线要点与失败策略：

| 要点 | 说明 |
|---|---|
| 色键只从边界连通 | 不删除物体内部的象牙色布料/骨器；边界合格种子 <40% 时转人工 |
| pivot 为权威 | 裁边、缩档、装箱只换坐标尺度，不得重新找中心；相邻关节误差 ≤1 px |
| 纹理采样 | 中心 1/3 区域取纹理片；遮罩前先去掉背景；不可把图标纸底平铺进衣甲 |
| 武器尺度 | 优先消费名录长度；缺失时用子类默认长度并登记 warning；`fitScale` 超 `[0.75,1.25]` 失败 |
| 确定性 | k-means 固定种子/色彩空间/迭代上限；输入、配置、工具版本全写 provenance |
| 人工门 | 32 px 轮廓断裂、脸框遮挡、右衽翻转、武器握点偏移或主体被色键删 >8% 均拒绝自动发布 |

#### 5.4.8 裁边、装箱与元数据

1. 校验每个 rig set 恰有三视图×13 源 part，PNG 尺寸匹配 manifest，pivot/childJoint 在容差内；
2. 颜色与可选法线用同一裁切框，图块间透明 padding 4 px；法线发布编码由 tech/06 处理；
3. `rectpack` 按 `rig_base` / `rig_equipment` 装入同一 atlas family，再把身份 rig 图页写入 `DataArrayTexture` 数组层；实例 flags 选层、shader 用 `sampler2DArray`，仍守 2 draw call；超层数先按区域装箱或降 ppm；
4. 图集元数据从 `manifest.yaml` 与每件装备 `layers.yaml` 派生，不另造角色动作 JSON。

### 5.6 图标批量生成（`ico_`）

#### 5.6.1 总体策略

1. **图标本体与边框分离**：武学/Buff/UI 本体是透明底 512² 母版；AR-22 的物品/装备从审定原图确定性派生 256/128/64/32 小图（§5.4.7），不再反向放大为 512²。品阶边框、稀有度光效、数量角标全部**运行时合成**（DOM/CSS 或 WebGL 精灵层）。原因：外来压制（基准 §3）使同一物品/武学在不同书界显示不同品阶，边框必须动态。
2. **模板化提示词**：每个子类一个模板，填入"主体意象 + 意象修饰 + 大阶氛围"，批量生成，人工只挑选。

#### 5.6.5 武学图鉴插画（秘籍图谱，`ill_`）

- 风格：仿古代武学图谱/经络图——白描人形 + 动势箭头 + 经络线，S2 纸本淡设色，**不写字**（招式口诀由 UI 排版）。
- 生产：取该武学代表招式的 `anim.clip` → 在 Blender 中用中性人形摆关键帧 → 渲染 Line Art 正/侧线稿 → 通过 TraeX/Gemini 低变化量风格化或在 Krita 手工上墨 → 叠加经络/气流纹样层；姿势源版本写入 `inputs`。
- 数量与等级：只为天级 51 + 地级 169 生产独立图鉴插画，即 `51+169=220` 张；玄/黄级共 `459+459=918` 门复用子类通用图谱。武学总量仍为 `51+169+459+459=1,138`，不可把 220 张插画误报为武学数（Canon v1.2 §4；`design/05` §14）。

#### 5.7.3 2.5D 视差分层（首选技法）

1. 关键帧 → Krita 人工蒙版分成 3–6 层（远山、中景、人物、前景雾/枝叶）→ 人工修层边；缺失背景以当前图像入口按蒙版补全，结果重新审核；
2. Blender 中按深度摆放各层平面，相机做缓慢推移/横移，层间加体积雾与墨晕 shader；
3. 优点：**确定性、可无限修改、零"AI 抖动"、成本近乎为零**；适合天书现世、书眠、书界开篇的意境镜头——这恰是水墨美学"以静写动"的表现方式。

#### 5.8.3 配音（可选）

- **预留流程**：Ink 以 `#vo:<line_id>` 标记 → `tsgen vo extract` 导出台词表 → 授权后每句生成候选并人工挑选 → 响度 −16 LUFS → `vo_<speaker>_<line_id>`。文本哈希变化将语音标为 `stale`；当前未生成语音。

| 层 | 内容 | 位置 | 备份 | 规模估算（全量） |
|---|---|---|---|---|
| `source` | 可编辑源：PSD/KRA、`.blend`、分层、当前入口下载的原始候选（含必要落选） | 本地工作盘 `/art/source`（实际根目录由配置给出） | rclone 增量同步到**私有**对象存储桶（冷存储层） | 300–500 GB【建议值】；每月按登记引用清理无用候选 |
| `master` | 审定母版（无损 PNG/WAV/ProRes）+ 元数据 | 本地 `/art/master` | 同步到私有桶（标准层）+ 一份离线硬盘 | 60–120 GB |
| `work` | 临时工作区：渲染中间帧、EXR、下载缓存 | 本地 `/art/work` | 不备份，可随时删除重建 | 视任务而定 |
| `runtime` | 压缩产物（KTX2、WebP/AVIF、Opus、MP4）+ manifest | 由 **tech/06** 构建并发布到 CDN（内容哈希命名） | 可随时由 master 重建 | 按书界分包，见 tech/06 |

- 统一 URI：登记库中路径写作 `art://master/portrait/ch01/<file>`，由 `tsgen` 按本机配置解析为实际路径或桶地址；**登记库只存路径 + sha256**，二进制永不进 Git。
- 不使用 Git LFS（托管配额贵、个人项目没必要）；若需版本化大文件，备选 DVC（远端指向同一私有桶）。
- 私有存储拓扑引用 tech/06：本版为本地离线副本 + Cloudflare R2 私有桶 / 同源 Worker，不备案、不启用国内或香港镜像；本文只额外要求 `source`/`master` **不可公开读**（金庸 IP 素材不得外泄，§9）。

### 6.4 资产登记库（对接 tech/06）

**定位**：登记库是"**每个资产是什么、处于什么状态、从何而来、母版在哪**"的唯一事实来源。tech/06 的构建脚本只消费 `status ∈ {approved}` 的条目生成 runtime 产物与 manifest；未审定的资产在开发构建中以占位图替代。

**与 tech/06 的约定**：
1. 登记库 `keys[]` 的每个 `AssetKey` 才是运行时 manifest 主键，并与资产 `id` 按 `tech/06` §3.2 双射；产物文件名使用内容哈希。`runtime.manifestKey` 若在生成类型中暴露，只能由 `id/keys` 派生，**不得回写 YAML**；
2. `files.master.sha256` 变化即触发该资产重新构建；
3. `chapter` 只提供时代提示；最终归包由 `tech/04` 的 `refs.json`、`design/11` 区域/时代映射与显式覆盖共同决定，跨时代稳定资产进 `region-<rg_id>` / `common`，时代差量进 `era-chNN`，不能仅凭 `chapter` 猜包；
4. Schema 唯一定义在 `packages/data`（Zod，符合 tech/01"内容 schema 唯一定义"的原则与基准 §19"YAML + Zod"），导出的 `asset.schema.json` 供 Python 侧生成模型；CI 的内容校验（`content:validate`）同时校验登记库。
5. `tsgen plan` 只从 `tech/04 content:build --emit-refs` 的引用图和归属文档生成待办：地图读取 `design/11/19` 与 `design/map/*.yaml`，门派读取 `design/17` 的 99 项闭集，NPC/变体读取 `design/18` 与 `design/catalog/npcs-*.md`；不得维护手写的城市、门派或人物生产名单。

### 6.5 状态机与溯源

```mermaid
stateDiagram-v2
  [*] --> todo: tsgen plan（由策划目录生成）
  todo --> generating: tsgen gen
  generating --> draft: 候选产出
  generating --> todo: 失败/超时
  draft --> review: 人工挑选 + 修图完成
  review --> approved: 清单通过
  review --> draft: 打回（记录原因）
  approved --> stale: 上游 inputs 版本变化 / spec 变化 / 台词文本变化
  stale --> generating: 重新生成或重渲
  approved --> deprecated: 设计删除或被替代
  draft --> deprecated
  deprecated --> [*]
```

| 状态 | 中文 | 说明 |
|---|---|---|
| `todo` | 待生成 | 已登记需求，尚无产出 |
| `generating` | 生成中 | 已提交任务（记录 provider 任务 ID，断点续跑） |
| `draft` | 草稿 | 有候选，未完成挑选/修图 |
| `review` | 待审 | 等待按清单审核 |
| `approved` | 通过 | 母版锁定，可被构建 |
| `stale` | 过期 | 上游变化，需重做；构建时仍用旧母版并告警 |
| `deprecated` | 废弃 | 保留记录与母版哈希，不再构建 |

**stale 传播**：`tsgen registry check` 构建依赖图（`inputs`），任一上游 `@版本` 变化 → 下游全部标 `stale`。例：修改段誉设定卡（`ref_…@3 → @4`）→ 立绘、头像、identity rig、装备预览、相关 CG 全部标记；整身人形图仅允许 cutin，并只标其直接依赖。未启用 LoRA 不应出现在当前依赖图中。

**溯源元数据写入文件本身**（冗余于登记库，防丢失）：PNG 写 iTXt/XMP（`tianshu:assetId`、`tianshu:ai=true`、`tianshu:provider`、`tianshu:model`），WAV 写 `INFO` 块，MP4 写 `comment` 元数据。运行时 WebP/AVIF 与 KTX2 默认不回写溯源字段；完整追溯依赖 manifest `src`、登记库与构建记录，见 `tech/06` §10。

生成请求与导入逻辑（登记库驱动；节选）：

```python
# tools/aigc/tsgen/cli.py（核心路径示例；完整工具还须包含依赖注入与异常处理）
from datetime import datetime, timezone
from hashlib import sha256
from pathlib import Path

@app.command()
def generate_request(type: str, chapter: str = "ch01", status: str = "todo", n: int = 4):
    for item in registry.query(type=type, chapter=chapter, status=status):
        spec = specs.load(item.spec)
        prompt = prompts.render(spec.template, subject=item.subject, variant=item.variant)
        blacklist.assert_clean(prompt)
        refs = registry.resolve_refs(item.inputs)
        request = requests.build(
            item=item,
            capability="image_generation",
            provider="traex",
            prompt=prompt,
            refs=refs,
            count=n,
        )
        requests.write_yaml(request)

@app.command()
def import_candidate(request_id: str, file: Path, displayed_model: str | None = None):
    request = requests.load(request_id)
    raw = file.read_bytes()
    source_uri = storage.copy_to_source(file, sha256(raw).hexdigest())
    registry.add_candidate(
        request.asset_id,
        source_uri,
        provenance={
            "provider": request.provider,
            "entrypoint": request.capability,
            "displayModel": displayed_model,
            "seed": None,
            "reproducibility": "best_effort",
            "requestId": request_id,
            "importedAt": datetime.now(timezone.utc).isoformat(),
        },
    )
    registry.set_status(request.asset_id, "draft")
```

上述片段只描述接口边界，`registry`、`requests` 与 `storage` 是 `tsgen` 内部服务，并非可直接复制运行的完整脚本。实现验收需覆盖：路径穿越拒绝、SHA-256 重复导入幂等、请求 ID 与资产 ID 一致、原文件不可被后处理覆盖、未核许可的候选不能进入 `approved`。

常用命令一览：

| 命令 | 作用 |
|---|---|
| `tsgen plan --from design/catalog/skills-shaolin.yaml` | 从策划目录批量生成登记条目（todo） |

| `tsgen import-candidate <request-id> <file> [--displayed-model <name>]` | 导入 TraeX 结果或 Gemini 网页下载原文件并写哈希/溯源 |

### 7.2 识别锚（identity anchors）

每个有立绘的角色在角色卡中必须写：**3 条面部/体态识别锚 + 1 组主配色 + 2 个剪影特征**。它们是：提示词的固定片段、审核清单"一致性"项的判据、跨年龄变体唯一不可变的部分。精灵（5.5 头身）与立绘（7–7.5 头身）比例不同，但识别锚与配色必须一致。

|---|---|---|---|---|
| 风格卡 | `style.yaml@主.次.补丁` | 线条、色阶、纸纹、禁用项、3 张通过样例与 3 张反例【建议值】 | 拼入请求并供人工并排审核 | 主版本变化触发全库影响分析；只强制重审 S 级 |
| 角色卡 | `characters/<npc_id>.yaml@版本` | 3 条识别锚、配色、剪影、时代服装接口 | 每个角色唯一文字源 | 任一锚变化使该角色各媒介资产 `stale` |
| 变体设定卡 | `ref_<npc_id>__<variant>_sheet@版本` | 正/侧/背、面部、服饰局部，均为审定母版 | 当前 `codex exec` 多参考输入 | 直接依赖的立绘、CG、identity rig、视频关键帧 `stale` |
| 请求快照 | `requests/<request-id>.yaml` | 展开后的提示词、参考图 ID+哈希、目标规格、入口 | 复现输入意图；网页/闭源输出仅 `best_effort` | 保留旧请求，不覆盖；重试产生新 attempt |
| identity rig | `assets/default/rig/<npcId>__<variant>/` | 具名 NPC 每变体一套三视图源件 | 复用骨架语义与动作轨迹，不与标准体混拼身份 part | 设定卡变化使对应 set 与预览 `stale` |
| 3D 代理（可选） | `mdl_<npc_id>__<variant>@版本` | 动物、建筑或获准战斗大动作的几何/骨架 | 不用于人形行走/待机主线 | 只使直接依赖的备选 `spr_*` 或 3D 产物 `stale` |

- **一次只改一个变量**：从设定卡生成姿势时不同时换服装；换服装时锁定脸、发型、体态和镜头。两项以上变化拆为串行请求并保留中间审定图。
- **参考数不硬编码**：当前两个入口的实际参考图上限、文件大小、导出分辨率和跨会话保留均按账号记录**（待实测）**。若上限不足，优先顺序为“面部 + 全身 + 当前服装细节”，而不是丢失身份锚。
- **没有虚假可复现性**：供应商未返回 seed/模型版本时写 `null`；以请求快照、参考图哈希、原下载文件哈希和人工修改记录保证可追溯，不承诺相同输入得到相同像素。
- **LoRA 只是未来迁移候选**：P02 明确不运行本地模型、不租卡，当前不创建 `lora:*` 资产、不预估训练步数，也不把闭源输出整理成训练集。若作者以后改变决定，须先逐项核对训练素材许可与服务条款，再另写训练方案。

### 7.4 金样本回归（Golden Set）

- 固定 **30 条【建议值】**回归请求：3 档风格 × 10 个典型用途（立绘、CG、场景、图标等）；固定请求文本、参考图与输入哈希。当前入口无公开 seed 时不写“固定种子”。
- 入口展示模型、提示词主版本、参考卡或关键后处理变化 → 重跑回归请求 → 生成同版式联系表 → 按线条、色阶、身份锚、文字污染、构图各自评分 → 人工并排审阅。P02 下不额外下载 DINO/CLIP 模型；可用尺寸、alpha、色板偏差等确定性指标辅助筛查。
- 风格模板**主版本号**变化（如 `style.yaml 1.x → 2.0`）意味着所有依赖资产进入 `stale` 评估：S 级强制重审，是否重做以差异和使用场景决定；A/B 级按需，不能因版本号机械重生成。

## 8. 预算与排期

> 前提：个人业余开发，每周 12–15 小时；P02 已明确**无本地显卡、不跑本地生成模型、不租卡**。人物 / 三视图走 `codex exec`，物品走 Gemini 网页版；账号额度、订阅与导出规格尚待实测。真正稀缺的是人工审核、分件修图、关节对位、三视图与装备穿插质检时间。

### 8.1 算力与硬件方案

| 资源 | 当前决定 | 成本口径 | 验收/退路 |

### 8.3 人工工时估算

**2026-10-01 AR-22 重估声明**：旧表的垂直切片约 624 h、每书界标准档约 516 h、精简档约 270 h，以及据此推得的全量约 6,300/4,200 h，均建立在“3D 人形建模 + 共享动作库 + 八向整身帧质检”上，现仅作为 **AR-22 前历史基线** 保留，不能继续用于排期或对外承诺。删除旧行并不等于相同工时自动节省；分层拆件、关节对位、三视图 z 序和装备覆盖层会产生新成本。

首批重估按以下计时桶登记，单位工时与新总量都以实际 P50/P80 回填，不先编造替代总数：

| 计时桶 | 计量单位 | 必记工作 | 首批退出条件 |
|---|---|---|---|
| `rig-sheet-and-cut` | 角色 / 体型 | 三视图生成与重试、关键点检测 / 修正、39 源件切分与遮挡补画、pivot 旁注、z 序 | 先主角·男 39 图全过动作原型；铺开时男女标准体 78 图全过 RIG-V01～V06 |
| `item-layer-tool` | slot/子类 | 色键、裁边、主色/纹理采样、模板填充、武器主轴与握点 | 十一类物品至少一件端到端通过；不可见类也有明确报告 |
| `item-layer-review` | 目录项×适用 slot | 三视图轮廓、穿插、握持、镜像、轻/中/重步态预览 | `layers.yaml` 与覆盖图齐全，失败项可追到源图 |
| `rig-runtime-integration` | 场景 | 统一图集、实例缓冲、两段式绘制、法线开关、Dir8 转向 | ENG-12 在 100 角色基准场景出 P50/P95 |
| `rig-preview-regression` | rig set / 装备组合 | 待机、走、跑、转向、披风/兵器二阶跟随的姿势条带 | `tools/rig/preview.py` 金样本差分通过 |
| 非角色资产 | 沿原资产类型 | 概念图、立绘、CG、地形建筑、图标、VFX、UI、地图、音视频 | 继续沿登记库实耗计时，不受 AR-22 数量公式直接推导 |
| 战斗动作片段 | 片段专项 | 动作源登记、骨架映射、烘焙、投影 / 剑轴 QA、事件对齐与 A/B | 全部走分层部件；整身帧只计 cutin，不计战斗动作 |

`tsgen budget` 在取得首批实耗前同时显示“历史基线（不可排期）”与“AR-22 新基线（采样中）”；至少完成一套男女基础 rig、每个可见装备槽一个样本及 ENG-12 场景压测后，才可发布新总工时。每周 12–15 h 的个人投入前提不变，仍默认逐书界、精简档推进。

结论与建议：
1. 这是个人项目最大的现实约束：**默认采用"精简档"作为每书界的完成线**，把"标准档"作为作者有兴趣时的扩充目标；
2. 由于是作者自娱，**逐书界推进、做完即玩**，不需要等全作完成；
3. 工具能力会变化，供应商适配器化允许替换入口；但只有回归集通过且实测工时下降后才能下调预算；
4. `tsgen budget` 每周输出剩余工时，按等级砍需求（先砍 B 级 CG 与次要立绘，最后才动 S 级）。

### 9.3 肖像与声音

- **演员肖像**：《民法典》第一千零一十九条禁止利用信息技术手段伪造等方式侵害他人肖像权；本项目**任何角色不得与任何演员相像**。审核中"像某某"即重做，不讨论相似程度。
- **声音**：《民法典》第一千零二十三条规定对自然人声音的保护参照适用肖像权保护的有关规定；**禁止克隆任何真人声音**（含影视剧配音、主播、公众人物）。当前 P02 下不生成配音；若未来经作者另行启用 TTS，也只能从抽象文字属性设计新音色，并先通过服务条款与相似性审核（§5.8.3）。
- **作者本人**：若用本人视频做动捕，只提取骨骼动作，不保存可识别的人脸素材到 `source` 以外位置。

- 《人工智能生成合成内容标识办法》自 2025-09-01 施行，对生成合成内容服务提供者、传播服务提供者和用户分别规定标识义务；其中用户发布可能导致公众混淆或误认的生成合成内容时，应主动声明并使用平台提供的标识功能。当前本项目不对外发布，不能仅据此断言具体条款一定适用于离线母版；仍把下列做法作为工程自律，若发布则重新做法律与平台规则审查：
